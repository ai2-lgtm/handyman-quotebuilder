Internal architecture reference

How the Quote Builder is put together

A plain-language walk through the system Handyman.ae's 7–8 staff use daily: what runs where, how a request moves through it, what the database looks like, and what to watch running this on Railway.

Stack Python 3 stdlib + SQLite + vanilla JS Hosting Railway (single container) Concurrent users ~7–8 Dependencies zero (pip)

01System at a glance

One Python process does everything: it serves the static front end, answers every API call, and talks directly to a single SQLite file. There's no separate database server, no build step, and no background workers — by design, for a tool this size.

Every browser talks to the same process; that process is the only thing that talks to the database file.

02Tech stack

Chosen deliberately for a small internal tool: nothing to install, nothing to build, nothing to patch for CVEs in a dependency tree.

LayerWhat it isWhy
Backendserver.py — a raw WSGI app (application(environ, start_response)), routed by hand with re.match against /api/... pathsNo framework tax; every route is a plain Python function you can read top to bottom
Authauth.py — Google OAuth only, domain-restricted, session tokens in SQLiteNo passwords to store, reset, or leak

Dependenciesrequirements.txt is emptyStandard library end to end

03What happens when someone signs in

There's no password anywhere in this system. Google verifies the person; the app only checks which domain their email belongs to.

  1. Redirect to Google
    GET /api/auth/google/start generates a random state token (CSRF guard), stores it in oauth_states, and redirects to Google's consent screen.
  2. Google calls back
    GET /api/auth/google/callback checks state, exchanges the auth code for an access token, and reads the person's email.
  3. Domain check
    The email's domain must be one of handyman.ae, kenzieclean.ae, legacygroup.me — anything else is rejected before a session is ever created.
  4. User row + role
    First sign-in creates a row in users. Role is staff by default, or admin if the email is in admin_allowlist — set once at boot from ADMIN_SEED_EMAILS, editable after that from Users & Access.
  5. Session cookie
    A random token goes into sessions (30-day expiry) and back to the browser as hm_session — HttpOnly, SameSite=Lax, and Secure whenever FORCE_SECURE_COOKIE=1.
  6. Every request after that
    get_session_user() reads the cookie, joins sessions → users, and hands the route its caller — or 401s. Routes that need role='admin' check it explicitly and 403 otherwise.

05Handling 7–8 people at once

This is the part worth understanding precisely, because it's also the system's tightest constraint.

Request handling
1 thread / request
ThreadingMixIn over Python's built-in wsgiref server — every request gets its own thread, so 7–8 people clicking around concurrently is not a bottleneck on its own.
Database writes
1 writer at a time
SQLite allows one writer across the entire file. A second save that arrives mid-write queues for up to busy_timeout=5000ms, then fails if the first still hasn't finished.

In practice, a quote save takes single-digit milliseconds, so two staff saving within the same 5-second window essentially never collide — this comfortably covers 7–8 people. It stops being comfortable if usage grows into dozens of concurrent writers, or one request starts holding a write lock for longer (a large bulk import, say).

Every SQLite connection is opened fresh per request (get_conn()) and closed at the end of the function — there's no shared connection or pool to exhaust, and no connection state to leak between requests.

06Frontend model

One HTML file, one script, no router — "tabs" are just <section> elements toggled with display:none.

Where state livesWhat's there
Server (SQLite)Every quote, price book item, user, and setting — the single source of truth.
Browser memory (one JS closure)The quote currently being edited, the loaded Price Book catalog, the wizard's in-progress answers.
localStoragePer-browser convenience only, never authoritative: an autosaved draft of the open quote, the last technician/staff used, and which location (Dubai / MAG City) is active.

07Running on Railway

The Procfile (web: python server.py) runs the same entry point as local development — main() calls init_db() then starts serving. That has two direct consequences worth being deliberate about.

Bind address: HOST defaults to 127.0.0.1, which is unreachable from outside the container. Railway's routing needs HOST=0.0.0.0 set explicitly as an environment variable, or the deploy will look healthy in logs while serving nothing externally.
VariablePurposeRailway setting
HOSTInterface the server binds to0.0.0.0 — required
PORTListen portRailway injects this automatically
DATA_DIRWhere handyman.db livesA path on a mounted Volume — e.g. /data — or every redeploy silently resets the database
GOOGLE_CLIENT_ID / GOOGLE_CLIENT_SECRETOAuth credentialsFrom Google Cloud Console, set as secrets
GOOGLE_REDIRECT_URIOAuth callback URLYour Railway public URL + /api/auth/google/callback
FORCE_SECURE_COOKIEMarks the session cookie Secure1 — Railway serves HTTPS by default, so this should always be on in production

Container filesystems on Railway are ephemeral by default — anything written outside a mounted Volume disappears on the next deploy, restart, or scale event. Since handyman.db is the entire database, confirming DATA_DIR points at a real Volume isn't optional configuration, it's the difference between persistent and disposable data.

08Known limitations & recommendations

Nothing here is urgent at 7–8 concurrent users. Listed in the order they'd start to matter if usage grows.

Verify
Confirm the Volume is actually mounted at DATA_DIR
This is the single highest-impact thing to check — everything else in this document assumes the database survives a redeploy.
Don't scale horizontally
Keep this at one Railway replica
Two instances would each open their own connection to the same SQLite file (or worse, diverge onto separate Volumes). This architecture is single-writer by design — scale it vertically (more CPU/RAM on one instance), not by adding replicas.
Recommended
Turn on WAL mode
One line — conn.execute("PRAGMA journal_mode=WAL") in get_conn() — lets reads proceed while a write is in progress, instead of the default rollback-journal behavior where they briefly queue behind it. Cheap insurance as usage grows past 7–8.
Recommended
Back up handyman.db on a schedule
It's a single file — a nightly copy to external storage (S3, Railway's own backups, anywhere off-Volume) is the entire disaster-recovery plan and costs almost nothing to set up.
Informational
wsgiref is a development-grade server
It's what's actually running in production here (via main()), not just local dev — fine at this traffic level, but it wasn't hardened for the internet at large (slow clients, malformed requests). Worth swapping for waitress or gunicorn if this ever faces more than internal, allow-listed traffic.
Informational
passenger_wsgi.py is unused here
It exists for a SiteGround/Passenger deployment path that predates Railway. Harmless to leave, safe to ignore.
